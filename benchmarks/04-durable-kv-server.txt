================================================================================
TASK — a durable key-value server that survives being killed
================================================================================

Build a small key-value store: a server process holding the data, a command-line
client that talks to it over a local TCP socket, and an append-only log on disk
so that killing the server loses nothing that was acknowledged.

No database engine. No web framework. Standard library is enough; if you reach
for an installed third-party library, justify it in one line.

THE SERVER

  Started as:   python server.py <port> <datadir>

  It listens on 127.0.0.1:<port>, speaks HTTP/1.1, and keeps its state under
  <datadir>. It prints exactly one line to standard output once it is actually
  accepting connections, and nothing else while it is healthy. A client must be
  able to wait for that line instead of sleeping a fixed number of seconds.

  PUT    /kv/<key>       request body is the value  -> 204, empty body
  GET    /kv/<key>                                  -> 200, value as the body,
                                                       or 404 if absent
  DELETE /kv/<key>                                  -> 204, or 404 if absent
  GET    /stats                                     -> 200, a JSON object with
                                                       exactly the integer keys
                                                       keys, writes, deletes,
                                                       reads
  POST   /admin/shutdown                            -> 204, then the process
                                                       shuts down cleanly and
                                                       exits 0 within 2 seconds

  Keys are 1..128 characters from [A-Za-z0-9_.-]; anything else is 400. Values
  are arbitrary bytes up to 65536; larger is 413. Any other path or method
  answers 404 or 405 — you choose, but be consistent and tell me which.

  `reads` counts every GET /kv/ request including misses. `writes` counts every
  accepted PUT. `deletes` counts every accepted DELETE. `keys` is how many keys
  are present right now.

DURABILITY

  Every accepted PUT and DELETE is appended to a log file under <datadir> and
  forced to disk BEFORE its response is sent. Once the client has seen the 204,
  the write must survive the process dying one instruction later. On start, the
  server rebuilds its state by replaying that log.

  When the log passes 5000 entries the server compacts it: writes a fresh log
  holding one entry per live key, then puts it in place. The replacement must be
  atomic on Windows — a process killed in the middle of compaction must come back
  to either the complete old log or the complete new one, never to a torn file.
  Be careful here: the obvious rename call is NOT atomic on Windows when the
  destination already exists.

THE CLIENT

  python client.py <port> get <key>
  python client.py <port> set <key> <value>
  python client.py <port> del <key>
  python client.py <port> stats

  `get` writes the value to standard output and exits 0; on a miss it writes
  nothing to standard output, one line to standard error, and exits 1. `set` and
  `del` write nothing and exit 0. Any transport failure exits 2 with the reason
  on standard error.
